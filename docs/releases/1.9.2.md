# CarSync Music by Brayo 1.9.2 — connection and upload review

## Correct source baseline

This build is based on the upstream 1.9.1 release (`3f5f9f7db44d4cac9d90cb30e0fea9437710073f`), not the older 1.6 checkout. The supplied `CarSyncMusic-1.9.1-test (3).apk` reports package `app.carsync.music`, version 1.9.1, version code 25. Version 1.9.2 uses version code 26 and the same project signing key, permitting an in-place update.

The newer convoy dashboard, map/GPS features, voice and Bluetooth radio, acoustic calibration, playback continuity, guest music/video contributions, and automatic production-server selection remain part of this source tree.

## Changes

- Host MP3 and permitted guest MP3/MP4 uploads use 256 KiB chunks on a server advertising `resumable_media_upload_v1`.
- Upload progress shows a percentage and retry status. Transient failures retry six times, with backoff from 1 to 30 seconds. A paused guest file remains selected for retry instead of being silently skipped.
- Each retry reads the server's committed offset, so a lost response does not cause the same data to be uploaded again. Completed media is reused.
- Interrupted chunks remain private and do not advance the saved offset. Completed files must match the requested SHA-256 hash before playback or guest-queue publication. Guest upload grants and sharing permissions are rechecked before publication.
- Partial progress survives a backend process restart with its data directory retained. A restart after receiving the final chunk recovers verification and publication.
- A validated default-network change reconnects with the existing session identity. The current voice/microphone and location cleanup runs before reconnecting; the existing consent-based GPS recovery remains in place. Stale socket callbacks cannot authenticate a superseded connection.
- Host startup recovery reads the saved library directly, avoiding a race with the on-screen library loading.
- Existing 1.9.1 servers remain usable: the app uses whole-file uploads with progress and retries until the server advertises resumable support. These fallback retries start the file again.

## Deployment and testing boundaries

This is a local review build. The public backend is not deployed by preparing it. Full resume support needs the accompanying backend update. Existing free hosting may discard its data directory on replacement/redeployment; this change does not provision persistent storage.

Host session credentials are restored as before. Guest upload grants are temporary and must be requested again after a server restart. A guest can retry the retained selection while the app remains open; after force-stopping/reopening the app, select the unfinished guest file again to request a fresh grant and reuse its saved server offset. Pending guest batches are not persisted across app process termination.

## Two-phone acceptance test

1. Update both phones from 1.9.1 to 1.9.2 without uninstalling. Confirm imported music, saved playlists, calibration and automatic/custom server settings remain available.
2. On the existing server, confirm ordinary playback, guest MP3/MP4 sharing, radio and location still work. Resume is available only on the updated backend.
3. On an updated test backend, enable permitted sharing and upload a host MP3. Interrupt the network midway, then restore it. Confirm the percentage resumes from acknowledged data and the guest hears the completed song.
4. Enable guest contributions. Repeat with a guest MP3 and MP4. Check a failed file remains available under Retry upload, that other guests cannot upload without a grant, and that completed files appear in the queue once.
5. Switch each phone between Wi-Fi and mobile data. Both networks must reach the same backend. Confirm the session code and participant count stay stable, playback returns to the server position, the microphone does not remain stuck on, and previously consented location updates return.
6. Revoke sharing during an upload. Confirm incomplete media cannot be streamed and enabling sharing again requires fresh guest authorization.
7. Restart the test backend with its data directory retained. Confirm a host upload resumes; a guest should refresh its upload permission and resume. Playback intentionally recovers paused after a backend restart.
8. Test with the actual car speakers/head units. Record reconnect delays and audible drift. Player timestamps and automated tests do not verify acoustic alignment.

Physical two-phone behavior and the rendered UI must be checked on devices before treating this as a road-tested release.
